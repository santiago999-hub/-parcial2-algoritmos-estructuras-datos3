Diagnóstico Inicial

Contexto: el problema operativo

Datos del sistema actual

  • Recetas Médicas: turno por orden del traumatólogo (magnetoterapia, ondas de choque).
  • Resumen Semanal: demanda conocida de antemano por clínica.
  • Rol del profesional: ejecuta su grilla horaria asignada.

Cuello de botella

  • Aparatología ociosa/escasa: comprar equipos para todas las sedes es inviable.
  • Traslados inviables: cruzar toda la ciudad genera abandono de tratamiento.
  • Recepción lenta: búsquedas lineales de fichas por DNI en horas pico.
El Problema y la Solución

Flujo Operativo Integrado

Acoplamos al sistema existente leyendo las recetas previas para automatizar decisiones.

1. Recetas Previas
Lectura de órdenes médicas y estimación de demanda de equipos por clínica.
2. Admisión con ABB
Búsqueda de paciente por DNI en O(log n), validación de historial y tratamiento.
3. Logística con Grafo
Asignación de equipos desde Sede Hub; derivación si excede 20 min.
Estructuras Jerárquicas

¿Por qué ABB y no una Lista?

Complejidad O(log n)

  • En cada nivel descartamos la mitad de los registros.
  • Con 1.000.000 de pacientes, una lista hace 1M de pasos; el ABB hace máximo 20.
  • Baja de Pacientes: resolvemos los 3 casos con Sucesor Inorden.
Código Java

Implementación del ABB — Búsqueda y Baja

public class ArbolPacientes {
    public Paciente buscar(NodoABB actual, int dni) {
        if (actual == null) return null;
        if (dni == actual.paciente.dni) return actual.paciente;
        return (dni < actual.paciente.dni)
            ? buscar(actual.izquierdo, dni)
            : buscar(actual.derecho, dni);
    }

    public NodoABB darDeBaja(NodoABB raiz, int dni) {
        if (raiz == null) return null;
        if (dni < raiz.paciente.dni) raiz.izquierdo = darDeBaja(raiz.izquierdo, dni);
        else if (dni > raiz.paciente.dni) raiz.derecho = darDeBaja(raiz.derecho, dni);
        else {
            if (raiz.izquierdo == null) return raiz.derecho;
            if (raiz.derecho == null) return raiz.izquierdo;
            raiz.paciente = obtenerMinimo(raiz.derecho);
            raiz.derecho = darDeBaja(raiz.derecho, raiz.paciente.dni);
        }
        return raiz;
    }
}
Grafo No Dirigido Ponderado

Logística de Equipos y Sede Main

Decisiones estratégicas sobre la red

  • Ahorro de capital: equipamiento costoso concentrado en la Sede Main (Hub) y rotado según la demanda semanal.
  • Grafo disperso (Lista de Adyacencia): clínicas conectadas solo con vecinas cercanas, memoria O(|V| + |E|).
  • Plan B situacional: derivación filtrando aristas con peso ≤ 20 min.

public class RedClinicas {
    private Map<String, List<Ruta>> grafo = new HashMap<>();

    public int obtenerOrden() { return grafo.size(); } // |V| Sucursales

    public String resolverLogistica(String sedeOrigen, int maxMinutos) {
        for (Ruta ruta : grafo.getOrDefault(sedeOrigen, List.of())) {
            if (ruta.tieneEquipoDisponible && ruta.minutos <= maxMinutos) {
                return ruta.sedeDestino;
            }
        }
        return "PROGRAMAR_TRASLADO_DE_EQUIPO_DESDE_HUB";
    }
}
Arquitectura Limpia

Aplicación de Principios SOLID

  • Responsabilidad Única (S): ArbolPacientes gestiona únicamente la estructura de datos, separada de la lógica de negocio de la clínica.
  • Inversión de Dependencias (D): depende de abstracciones (interfaces como IBuscadorPacientes), permitiendo cambiar de motor sin romper la aplicación.
